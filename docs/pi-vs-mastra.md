# Pi与Mastra：实现方式和取舍

日期：2026-10-24。状态：比较后已确定首版直接使用Pi SDK，不采用Mastra；以下保留比较依据，未安装、集成或压测。两种方案都直接配置Tool，不要求MCP。

## 本项目需要解决什么

核心是管理一批持续工作的会话：按方向协作，或对同一输入进行多次尝试；默认每20分钟复用现有上下文生成独立汇报；新子证明通过submit_skill交给一个独立整理Agent和工作区。应用另有受限文件范围、Lean验收、成果图与项目导出要求。

比较应看整个项目还需要自建哪些能力。框架提供的功能必须能接入上述边界，才能算作节省工作；接口少本身不代表项目总复杂度低。

## 方案A：TS后台直接嵌入Pi SDK

1. 项目协调模块管理问题、任务、尝试、额度和文件范围。
2. 每个活动Agent使用独立Pi会话；主管、证明和整理按角色配置提示词与Tool。
3. Pi负责会话中的模型交互、Tool循环、历史记录及上下文处理。应用订阅事件，保存项目关联并更新界面。
4. 汇报时取得确定的上下文截止点，在独立会话中复用上下文并追加一句指令；原证明继续。
5. 应用负责项目级调度、重启后的任务恢复、成果库、验收和导出。

[Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)可嵌入Node.js/TS应用，提供会话、事件、工具和资源配置；[会话格式](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)以JSONL和父子关系保存历史。以上能力不等于已经具备本项目的百Agent调度器。

优势是会话、分支和上下文与本项目需求接近，文件记录容易随项目携带，应用可以明确控制角色与共享内容。代价是项目级可靠调度、恢复及监控需要自己实现；Pi已有的单会话能力仍应直接复用，避免再写一套Agent循环。

Pi原生分支/运行时fork会改变当前活动分支或会话。定时汇报应使用独立的会话状态，不能仅在工作会话上切换分支就当作并行汇报。具体快照与独立创建方式需针对选定版本验证。

## 方案B：使用Mastra的Agent与运行管理能力

1. 用Mastra Agent表达主管、证明和整理角色，注入项目自有的受限Tool。
2. 根据交互需要采用AgentController，创建独立Session和持久Thread；项目任务ID与这些记录关联。
3. 用Memory保存历史；在确定的截止点克隆所需消息，建立独立汇报Thread并追加指令。
4. 需要时采用后台任务、运行快照和恢复能力；submit_skill仍触发一个整理Agent，整理过程保持当前简单流程。
5. 应用消费事件和存储结果，生成成果图并导出文件、依赖版本与运行记录。

Mastra当前不仅提供Workflow。[AgentController](https://mastra.ai/docs/harness/agent-controller)管理独立会话及交互控制；[Harness](https://mastra.ai/docs/harness/overview)覆盖后台任务、持续目标等能力；[历史记录](https://mastra.ai/docs/memory/message-history)有对话克隆接口。开放证明过程可以使用Agent，步骤明确的外围流程再按需采用[Workflow](https://mastra.ai/docs/workflows/overview)。

优势是运行控制、存储、后台任务和调试工具已有框架支持，可能减少自建外围机制。代价是应用需理解并适配Session、Thread、Memory、Storage及相应生命周期；采用的能力越多，迁移时需要处理的框架数据也越多。这是工程判断，不是本项目开发量或性能实测。

[Durable Agents](https://mastra.ai/docs/harness/durable-agents)文档当前标为beta，恢复行为需要明确配置。恢复可能重新发出模型或Tool调用；外部计算作业仍需由项目保存作业ID并避免重复提交。持久化对话也不等于任意活动Session状态都会自动恢复。

## 对照本项目

| 需求 | Pi方案 | Mastra方案 |
| --- | --- | --- |
| Agent自主持续探索 | 复用Pi会话与Tool循环 | 复用Mastra Agent；无需把证明步骤全写成Workflow |
| 约100次尝试 | 项目自建调度与全局额度，使用多个独立会话 | 可复用会话和后台运行机制，项目仍控制模型请求及计算额度 |
| 20分钟上下文汇报 | 利用会话历史与分支资料，应用创建独立汇报状态 | 利用Thread消息查询/克隆，应用明确截止点与有效上下文 |
| 记录和恢复 | 会话文件直接复用，项目补任务恢复规则 | 可复用Memory/Storage及可选恢复机制，须核对实际保存范围 |
| 查问题 | 使用事件和原始会话，自建项目运行视图 | 可复用Studio、追踪和运行管理视图，成果图仍自己实现 |
| 导出与换机器 | 打包会话、文件、模块及项目状态 | 导出所用框架记录，再与文件及项目状态形成一致快照 |
| 换成物理/生物 | 增加领域Tool、任务规则和验收 | 同样增加领域Tool和验收，明确多步骤流程可复用Workflow |
| 长期维护代价 | 自建外围机制更多，项目自主控制更多 | 可复用机制更多，也需跟随框架接口与数据规则变化 |

表中的开发代价为根据架构推导的预期；没有对两边运行时间、内存或代码量做比较测试。

## 两边都需要由项目负责的内容

- 数学题意和形式化声明的一致性、Lean环境及验收证据。
- 各Agent的文件权限与只读共享成果；指定cwd或Thread ID不能代替权限检查。
- 先搜索再证明、独立整理Agent、固定版本成果目录和实际依赖关系。
- 成果图的节点语义、项目快照和完整导出。
- 上游模型配额、计算任务并发，以及外部作业的查询和重复提交控制。

Mastra的Memory或额外摘要机制不能默认替代本项目的“复用已有上下文，加一句汇报指令”。两边都要核对汇报实际看到的上下文，并保留原始记录。框架提供的对话复制也不保证模型服务端KV缓存可复制。

Mastra的[本地Storage](https://mastra.ai/docs/storage)可以使用文件型libSQL，无需仅因选择Mastra就强制部署独立数据库服务器。两种方案都可以嵌入本机应用；本轮没有证明其中一种在MacBook Air上更省内存或可稳定达到100真实并发。

## 选型依据

若当前优先级是控制会话上下文、管理许多独立尝试，并愿意自己维护一层精简项目调度，Pi值得优先验证。

若首版就希望较多复用后台执行、运行控制、持久化及调试机制，而且这些机制确实减少自建代码，Mastra值得优先验证。新增生物或物理领域本身不是必须选择Mastra的理由。

按《软件设计的哲学》的思路，应选择能把所需复杂度完整收进模块、让项目其他部分更容易理解的方案。首版直接使用Pi SDK。后续如进入实现，先在Pi上验证小链路：工作会话持续执行、独立汇报、submit_skill整理、保存后重启续接。再核验模型额度与规模，不先搭建完整通用平台。

2026-10-24比较后选择Pi SDK，原因是已有会话与上下文能力符合当前需求，项目愿意维护精简的全局调度与业务层。选择属于设计决定，不能替代容量和恢复验证；未安装依赖、调用模型、运行Lean或测量原型。
