# 按任务配置工具包：数学与生物

日期：2026-10-23。状态：资料调研与设计建议；未安装工具、运行任务或验证资源用量。

## 当前讨论结论

工具包按任务配置。证明、反例搜索、序列分析和模型推理可以使用不同工具包。工具包应描述可调用能力、固定软件环境、数据访问范围、资源要求和结果检查方法。包内软件依赖的数量与暴露给 Agent 的接口数量分别管理。

主 Agent 可以提出工具包需求，由后端按已有权限和资源条件分配。Worker 不应自行安装任意依赖、修改环境或取得未授权的远端资源。这是设计建议，具体工具包协议尚未实现。

## 数学的起步范围

对于已明确、可用 Lean 表达的题目，读取、写入和受控 Lean 交互可以构成最小闭环。这里的 Lean 交互应能反馈诊断和当前证明目标；固定 Lean/Mathlib 版本，提供本地定义和引理查找，可以显著减少盲目尝试。它不代表任何数学问题都能被解决，也不代表对所有题目都高效。

[lean-lsp-mcp](https://github.com/oOo0oOo/lean-lsp-mcp)实际提供诊断、goal、hover、搜索和多种尝试能力，说明 Lean 工具不宜只返回编译成功或失败。[Numina-Lean-Agent](https://github.com/project-numina/numina-lean-agent)还配有搜索、非形式化推理、代码变换和验证等能力；其 Python 运行依赖属于该实现的选择，不是数学证明必须开放 Python 的理由。

建议第一版数学包包含：受限读写、Lean 检查与目标状态、本地数学库查找。文献检索可以先由主 Agent 处理。遇到明确需要符号计算、组合搜索或求解器的任务时，再增加相应能力；候选结果仍需按任务标准独立验收。

## 生物需要按具体任务细分

| 任务 | 工具与环境示例 | 资源判断 |
| --- | --- | --- |
| 少量序列解析与统计 | Biopython 或同类序列工具 | 可从本机小样本开始测量；不能仅因“生物”就假定需要GPU |
| RNA测序分析 | FastQC、STAR/Salmon、SAMtools、统计与报告工具、参考基因组 | CPU、内存、存储和数据规模都重要，需按输入与步骤测量 |
| 蛋白结构预测 | 如AlphaFold 3的数据处理与模型推理流程 | 官方将CPU数据处理和GPU推理分阶段说明；适合为重步骤配置单独资源 |

[Biopython教程](https://biopython.org/docs/latest/Tutorial/index.html)覆盖序列读写、比对和数据库访问。[nf-core/rnaseq](https://nf-co.re/rnaseq/latest/)展示真实测序流程如何组合多种工具、参考数据、质控和结果报告。[AlphaFold 3性能文档](https://github.com/google-deepmind/alphafold3/blob/main/docs/performance.md)区分CPU数据流程与GPU推理，资源需求随输入和硬件变化。这里没有为这些任务给出统一硬件下限，也没有本项目实测。

不需要把所有生物工具都装进每个Worker环境。依赖可锁定在任务环境中；小任务本地运行，大任务提交到已有授权的服务器或集群，返回任务编号、状态、日志和产物。[Nextflow executor](https://docs.seqera.io/nextflow/executor)已有将同一流程映射到本机、HPC或云执行系统的机制，可以作为后续执行适配的参考；它本身不会提供算力。

## 验收方式也随工具包变化

数学包以准确的形式化目标和证明依赖检查为核心。生物分析需要同时记录数据、参考数据库版本、方法参数、质控、统计假设和复现结果。程序成功退出不能证明科学结论成立；预测或统计关联也不能直接当作数学意义的证明。

## 第一版建议

先实现数学基础包，并保留按任务绑定工具包和资源的边界。不要预装“全学科环境”，也不要把生物、物理和数学都限定为同一种验证方式。重计算并发与Agent会话数量分别调度。

扩展时先增加一个明确任务的工具包，并用小样本验证依赖、资源、输出与验收，再扩大输入规模。工具包说明或skill只能指导使用；实际权限、软件安装状态和算力必须由运行系统提供。

## 同一次证明中的定时整理与逐步展开（规划）

2026-10-23用户澄清：模块提取与共享发生在当前证明持续运行期间。定时总结基于现有上下文，同时更新任务进展并整理已经形成的子证明模块，供本次主流程和并行Agent按需使用；不以“下一轮研究”或“新任务启动”为生效前提。这覆盖此前把定时审查仅描述为兜底、把共享主要描述为后续复用的表述。

主流程具有一个文件夹入口，简短说明主目标、当前路线、模块索引和阻塞。Agent先读入口，再按需展开相关子模块；不把所有证明、脚本和历史记录一次性灌入上下文。文件名和目录形状是规划示例，尚未实现或生成实际skill。

每个子模块文件夹同时保存说明和可调用成果：说明记录准确的子问题、前提、输出、使用方法、依赖、状态以及它如何推进父目标；实际成果可以是Lean源模块，也可以是受控调用的脚本及证书。数学主证明直接引用已验证的Lean引理。脚本产生的候选或计算结果，须满足相应验收要求后才能成为已证明事实。skill式说明负责导航和解释，可执行性来自包内实际资源和工具授权。

每次定时整理输出两个相互关联的结果：

1. 节点进展：做了什么、有哪些证据、当前阻塞、下一步、持续时间。
2. 模块清单：新形成或更新了哪些模块、对应父目标中的哪一步、目前可否直接调用、如何按需展开。

思维图节点可以展开查看关联模块、证据和调用入口。主Agent收到索引更新后，在当前证明中继续分工或使用已完成子模块。模块也可供同次运行的其他Agent使用，后续任务复用属于额外收益。

整理者不能把尚未证明的内容标为已证明。模块可以按进行中、待验证、已验证等状态被索引，只有符合验收条件的成果才能作为主证明的已成立依赖。待证模块可作为计划中的子目标展示，不能偷偷成为主目标的假设。

Worker在自己的工作区形成候选，整理与验证流程负责受信发布。已共享版本保持可追溯，使用者固定所引用的内容版本，并在安全检查点显式接收更新；共享不意味着Worker互相修改文件。说明文件也不能改写冻结原题或授予工具权限。

每次整理保留所依据的上下文/文件版本、父子任务关联和验证结果。辅助引理数量不代表主问题进展；模块与父目标的实际依赖关系才是展示贡献的依据之一。

## 全局搜索与当前任务只读使用（规划）

同日进一步明确：成果整理过程沿用上述共识，重点转为全局共享库的发现与使用。所有Agent通过全局搜索工具查找已经整理的skill；选中并打开后，对应skill出现在当前任务目录中，供该任务只读使用。此处全局指研究系统的共享库，不扩大为个人文件或整台机器的访问权限。

建议接口只需明确两类能力：搜索返回名称、摘要、适用条件、验证状态和版本；打开返回当前任务内只读目录及入口说明位置。Agent先读简短入口，再按需读取子说明、Lean模块或脚本。默认搜索可复用的已验证成果；若查询进行中的模块，必须清楚保留未完成状态。

打开操作由受信工具服务完成，使用固定版本的只读快照或受系统限制的挂载，不仅依赖软链接或提示词。共享区和任务内只读副本均不能由Worker修改；需要改进时在自己的工作区形成新候选，再由既有整理/验证流程发布新版本。新的版本不会静默改变已有任务正在使用的内容。

skill可以包含Lean源码、脚本、参考资料和依赖说明。执行仍经过任务已有工具和沙盒权限；打开skill不自动安装依赖、授予网络或GPU权限。脚本结果写到当前任务可写输出目录，Lean生成物写入任务专用构建目录，不写入只读skill目录。工具链或依赖不匹配时报告具体不兼容，不把复制文件当作环境已就绪。
